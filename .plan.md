# Fase 5 — Plano de Implementação (`@repo/web`)

## Objetivo desta fase
Deixar o projeto Angular funcional dentro de `packages/web`, com base sólida de integração HTTP com a API (`/api/v1`) e autenticação JWT (`api` <-> `web`), sem planejamento/implementação de telas de negócio.

## Escopo (incluído)
1. Bootstrap do app Angular no pacote `@repo/web`.
2. Organização base de pastas conforme arquitetura (`core`, `shared`, `modules`, `layouts`).
3. Configuração de ambiente para URL da API.
4. Serviço base de comunicação com API.
5. Interceptor(es) HTTP para JWT e tratamento básico de erro.
6. Guard(s) de rota para proteção de páginas autenticadas.
7. Fluxo técnico de login/logout e sessão no frontend.
8. Ajustes na API para emissão e validação de JWT.
9. Tipagem de request/response usando contratos de `@repo/shared`.
10. Setup de scripts de execução/build no workspace.

## Fora de escopo (não incluir nesta fase)
1. Planejamento de telas.
2. Implementação de UI de módulos de negócio.
3. Telas avançadas de autenticação (recuperação de senha, cadastro completo, etc).
4. Estados complexos de feature (dashboard, relatórios, etc).

## Plano de execução

### Etapa 1 — Estruturar o pacote Angular
1. Inicializar `@repo/web` com Angular (build e serve funcionais).
2. Garantir `tsconfig` e `package.json` alinhados ao workspace.
3. Definir estrutura mínima:
   - `src/app/core`
   - `src/app/shared`
   - `src/app/modules`
   - `src/app/layouts`

### Etapa 2 — Configurar ambientes
1. Criar arquivos de ambiente com `apiBaseUrl` e URLs/portas de execução.
2. Definir política obrigatória por ambiente:
   - `FORTUNA_ENV=DEV`: usar padrão automático de desenvolvimento:
     - `FORTUNA_WEB_PORT=4200`
     - `FORTUNA_API_PORT=3000`
     - `FORTUNA_WEB_URL=http://localhost:4200`
     - `FORTUNA_API_BASE_URL=http://localhost:3000/api/v1`
   - `FORTUNA_ENV=PROD`: exigir explicitamente as variáveis:
     - `FORTUNA_WEB_PORT`
     - `FORTUNA_API_PORT`
     - `FORTUNA_WEB_URL`
     - `FORTUNA_API_BASE_URL`
3. Implementar validação de configuração com fail-fast:
   - se `FORTUNA_ENV=PROD` e alguma variável obrigatória estiver ausente/vazia, encerrar startup com erro claro listando quais faltam.
4. Centralizar acesso a configuração em `core/config` (web) e módulo de env equivalente na API.

### Etapa 3 — Criar camada HTTP base
1. Implementar `ApiClientService` em `core/http`.
2. Encapsular métodos base (`get`, `post`, `put`, `patch`, `delete`) com generics.
3. Padronizar retorno conforme envelope da API:
   - sucesso: `{ data, request_id }`
   - erro: `{ code, message, request_id }`
   - validação: `{ code, message, fields, request_id }`

### Etapa 4 — Interceptors e políticas de comunicação
1. Adicionar interceptor para `x-request-id` (quando necessário).
2. Adicionar interceptor de autenticação para enviar `Authorization: Bearer <access_token>`.
3. Normalizar erros HTTP em um formato único no frontend.
4. Tratar `401`/`403` centralmente (ex.: limpar sessão e redirecionar para login).

### Etapa 5 — Guard(s) e sessão frontend
1. Implementar `AuthGuard` para rotas protegidas.
2. Implementar `GuestGuard` opcional para bloquear login quando usuário já autenticado.
3. Criar `AuthSessionService` para guardar/ler estado autenticado.
4. Definir estratégia de armazenamento de token (preferência: access token em memória + refresh token seguro em cookie HttpOnly no backend).

### Etapa 6 — Fluxo de login/logout (sem foco em telas)
1. Criar `AuthService` com métodos `login`, `logout`, `me` e (se aplicável) `refresh`.
2. Integrar com endpoints de autenticação da API.
3. Garantir inicialização da sessão no bootstrap do app.
4. Deixar um componente/página mínima de login apenas para validação técnica do fluxo.

### Etapa 7 — Ajustes na API para JWT
1. Criar endpoints em `/api/v1/auth`:
   - `POST /login`
   - `POST /refresh` (se refresh token for adotado)
   - `POST /logout`
   - `GET /me`
2. Substituir middleware MVP baseado em `x-user-id` por middleware JWT.
3. Assinar tokens com segredo/config de ambiente.
4. Padronizar claims mínimas (ex.: `sub` = `user_id`).
5. Manter contratos de resposta no envelope padrão já existente da API.

### Etapa 8 — Contratos e tipagem compartilhada
1. Consumir tipos DTO/schemas de `@repo/shared` no `web`.
2. Evitar tipos duplicados locais para entidades já definidas em `shared`.
3. Adicionar contratos de autenticação no `@repo/shared` (login request/response, sessão do usuário autenticado).
4. Criar camada de mapeamento mínima apenas quando necessário.

### Etapa 9 — Validação técnica da fase
1. Build do `@repo/web` no workspace sem erros.
2. Execução local do app Angular.
3. Login válido retorna sessão JWT funcional no frontend.
4. Rotas protegidas bloqueiam acesso sem autenticação (`guard` ativo).
5. Requisições autenticadas enviam `Authorization` corretamente.
6. Testar erro de token expirado/inválido com tratamento centralizado.
7. Testar validação de env:
   - em `DEV`, defaults aplicados corretamente quando variáveis não forem definidas.
   - em `PROD`, startup falha com mensagem clara se faltar variável obrigatória.

## Entregáveis mínimos
1. `@repo/web` inicializado e executável.
2. Estrutura de pastas base criada.
3. Configuração de ambiente para API pronta.
4. `ApiClientService` funcional.
5. Interceptor de autenticação JWT implementado.
6. `AuthGuard` implementado e conectado ao roteamento.
7. `AuthService` com login/logout/me funcional.
8. Endpoints de auth JWT implementados na API.
9. Exemplo de consumo de endpoint autenticado com tipagem de `@repo/shared`.

## Critérios de aceite
1. `pnpm` consegue instalar/buildar/rodar `@repo/web` sem quebrar o monorepo.
2. Frontend chama API por serviço central (sem chamadas HTTP espalhadas).
3. Contratos compartilhados são reutilizados a partir de `@repo/shared`.
4. Comunicação `web` <-> `api` autenticada com JWT (sem `x-user-id`).
5. Guard de rota bloqueia acesso não autenticado.
6. Login/logout técnicos funcionam fim a fim.
7. Nenhum acesso direto a banco no frontend.
8. Nenhuma tela de negócio é obrigatória para concluir esta fase.
9. Regra de ambientes aplicada:
   - `DEV` usa defaults definidos.
   - `PROD` exige variáveis e falha de forma explícita quando ausentes.

## Sequência recomendada de implementação
1. Bootstrap Angular + scripts.
2. Estrutura de pastas.
3. Ambientes/config.
4. ApiClient.
5. Endpoints/middleware JWT na API.
6. AuthService + sessão.
7. Guards.
8. Interceptors JWT.
9. Exemplo de chamada autenticada tipada.
10. Build e validação final.
