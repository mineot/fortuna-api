# Plano de Implementação do Pacote `@repo/api`

## 1) Objetivo
Implementar a Fase 4 do projeto (`@repo/api`) com Hono, conectando os repositórios do `@repo/database` sem violar as regras de arquitetura do `.codex`:
- API como camada de orquestração
- sem SQL direto na API
- regras de negócio pesadas fora da API
- contratos/validação centralizados em `@repo/shared`

## 2) Premissas Obrigatórias
- Linguagem e stack: TypeScript + Hono + Zod + Kysely (via `@repo/database`).
- Versionamento de API: prefixo `/api/v1`.
- Formato de resposta: JSON.
- Erros padronizados com contratos de `ValidationErrorPayload` e `DomainErrorPayload`.
- Identidade de usuário no MVP: middleware `x-user-id` (temporário), com evolução posterior para autenticação real.
- Build de produção do pacote API: JavaScript gerado com `tsc` + declarações `.d.ts`.

## 3) Estado Atual (2026-05-16)
- `packages/api` existe apenas como scaffold:
- `src/index.ts` vazio
- `src/server.ts` vazio
- sem dependências HTTP no `package.json`
- sem módulos, rotas, middlewares, validações e testes

## 8) Estratégia de Segurança e Autenticação (MVP -> Evolução)
- MVP técnico:
- `auth-user.middleware` exige `x-user-id` inteiro positivo em rotas protegidas.
- rotas públicas iniciais: `health`, `create user` (e futuramente login).
- Evolução planejada:
- introduzir módulo `auth` com hash de senha e emissão/validação de token.
- substituir `x-user-id` por identidade vinda de token.

## 10) Riscos e Mitigações
- Risco: acoplamento excessivo da API com detalhes de banco.
- Mitigação: consumir apenas interfaces dos repositórios via fábrica central.
- Risco: inconsistência de contrato entre módulos.
- Mitigação: usar schemas e tipos de `@repo/shared` como fonte única.
- Risco: regressão no fluxo de cartão (duplicar despesa).
- Mitigação: testes específicos de compra x pagamento de fatura.
- Risco: ausência de autenticação final no início.
- Mitigação: middleware temporário explícito + backlog de autenticação real.
